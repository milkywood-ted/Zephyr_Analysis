# 분석 스크립트

문서의 수치와 인용을 **재현·검증**하기 위한 스크립트입니다.

## 전제

이 저장소가 west 워크스페이스 안에 있어야 합니다. 두 스크립트 모두 자기 위치를 기준으로 소스 트리를 찾으므로 별도 설정이 필요 없습니다.

```
<west workspace>/
├── zephyr/            # 분석 대상 소스
└── <이 저장소>/
    └── scripts/
        ├── verify_refs.py
        └── include_graph.py
```

Python 3.9 이상이면 동작하며 외부 패키지 의존이 없습니다. 워크스페이스에 `.venv`가 있다면 그것을 쓰면 됩니다.

## `verify_refs.py` — 인용 검증

모든 문서의 마크다운 링크와 핵심 인용이 실제 소스와 맞는지 확인합니다.

```sh
../../.venv/bin/python3 scripts/verify_refs.py   # 저장소 루트에서
```

검사 항목은 세 가지입니다.

1. **링크 유효성** — 모든 링크의 대상 파일이 존재하는지, 행 번호가 파일 길이를 넘지 않는지, 범위가 역전되지 않았는지
2. **인용 내용 일치** — `ANCHORS` 목록의 각 항목에 대해, 지정한 행에 기대한 코드가 실제로 있는지
3. **절 참조(§) 유효성** — `04-....md §6.3`, `02 §7`, `본 문서 §4.2` 같은 참조의 대상 절이 실제로 존재하는지

3번은 문서를 고칠 때 절 번호가 조용히 어긋나는 것을 잡습니다. 링크 검사로는 걸리지 않는 종류의 오류입니다.

§ 참조의 귀속은 휴리스틱입니다 — 같은 줄에서 § 앞 40자 이내에 문서 지시자가 있으면 그 문서, 없으면 자기 문서로 봅니다(`본 문서`가 앞에 오면 항상 자기 문서). 표 한 줄에 여러 참조가 섞인 경우까지 대체로 맞지만 완벽하지는 않으므로, 실패가 나오면 **문서가 아니라 귀속이 틀렸을 가능성**도 함께 보십시오.

링크는 두 기준을 모두 허용합니다 — 분석 문서는 워크스페이스 루트 기준(`zephyr/kernel/sched.c`), README는 저장소 루트 기준(`00-분석-개요.md`)입니다.

성공 시 종료 코드 0, 실패가 하나라도 있으면 1을 반환하므로 CI에 걸 수 있습니다.

**새 문서를 쓸 때는 `ANCHORS`에 핵심 인용을 추가하십시오.** 링크 유효성만으로는 "행 번호가 밀렸지만 여전히 파일 안"인 경우를 잡지 못합니다.

## `include_graph.py` — 계층 의존 측정

[08-계층과-의존-구조.md](../08-계층과-의존-구조.md)의 의존 행렬을 만듭니다.

```sh
../../.venv/bin/python3 scripts/include_graph.py
```

출력은 네 부분입니다.

| 출력 | 내용 |
|---|---|
| 계층 간 include 행렬 | 행=포함하는 쪽, 열=포함되는 쪽 |
| 미해결 include | 해석하지 못한 건수 (오차 범위) |
| 커널 내부 헤더 사용처 | `kernel/include/*.h`를 포함하는 계층별 횟수 |
| arch 헤더 사용처 | `arch/**/*.h`를 포함하는 계층별 횟수 |

### 한계

C 전처리기가 아니라 **텍스트 기반 해석기**입니다.

- 조건부 컴파일(`#if`)을 평가하지 않으므로, 실제 빌드에 포함되지 않는 `#include`도 셉니다
- 같은 이름의 헤더가 여러 곳에 있으면 경로가 가까운 쪽을 고릅니다 (아키텍처별 헤더에서 발생)
- 빌드 시각 생성 헤더(`zephyr/offsets.h`, `zephyr/syscalls/*`)와 툴체인 헤더는 해석되지 않고 **미해결로 집계**됩니다

따라서 수치는 **경향과 크기 비교용**이며, `drivers`·`soc`처럼 미해결이 많은 행의 절대값은 하한으로 읽어야 합니다. 08 §1이 이 오차 범위를 문서화하고 있습니다.

## `check_quotes.py` — 인용 코드 블록 대조

문서에 실린 코드 블록이 **소스에 실재하는지**, 그리고 **문서가 그 위치를 인용하는지** 확인합니다.

```sh
python3 scripts/check_quotes.py
```

인용과 블록을 근접도로 짝짓는 방식은 오탐이 많아 쓰지 않습니다. 대신 블록을 소스에서 먼저 찾고(생략 허용), 그 위치를 가리키는 인용이 같은 문서에 있는지 확인합니다.

| 결과 | 의미 |
|---|---|
| 위치 확인 + 인용됨 | 정상 |
| **위치는 확인되나 인용 없음** | **결함** — 독자가 원문을 확인할 방법이 없음. 종료 코드 1 |
| 소스에서 찾지 못함 | 대개 서술상 재편집. 아래 참조 |

세 번째는 실패로 보지 않습니다. 문서는 원문 복사가 목적이 아니라서 여러 줄을 한 줄로 합치거나, 인자 목록을 `...`로 줄이거나, `#ifdef` 두 갈래를 한 줄로 병합합니다.

다만 **식별자를 바꿔 인용하면 독자가 소스에서 검색할 수 없으므로** 그것은 고쳐야 합니다. 실제로 이 검사가 `z_sched_prio_cmp()`의 인자를 `thread_1`/`thread_2` 대신 `t1`/`t2`로 적은 사례를 잡아냈습니다. 출력 목록은 그런 사례가 섞여 있는지 눈으로 확인하는 용도입니다.

## `count_mechanisms.py` — 확장 메커니즘 집계 재현

[09-확장-메커니즘.md](../09-확장-메커니즘.md)의 수치를 다시 세어 문서 값과 대조합니다.

```sh
python3 scripts/count_mechanisms.py
```

불일치가 있으면 종료 코드 1과 함께 어느 항목인지 보고합니다. 소스 트리가 갱신되면 수치는 자연히 변하므로, **불일치는 곧 문서를 갱신하라는 신호**이지 오류가 아닙니다.
